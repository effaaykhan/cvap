# P3.3 release resolution — design (B25)

**Status (session-31): BUILT and shipped (ADR-064, ADR-065).** The resolver, the store read, the
correlate wiring, the dashboard and the end-to-end acceptance all landed; see the session-31
ledger entry. Two things the build measured and recorded honestly, refining this design: (1)
confidence is **tiered by vote count** (2/3/4+), not a flat agreement ratio, so a two-vote
resolution is distinguishable from a four-vote one (ADR-065). (2) **Coverage is bounded by
service identification.** Running Metasploitable's 11 banners through the real matcher
(`TestMetasploitableVersionCoverageMeasured`) yields a version for **5 of 11** — four in safe
mode (vsftpd, openssh, mysql, proftpd) plus Apache httpd 2.2.8 under intrusive HTTP probing — of
which **two band-vote hardy in safe mode** (openssh, mysql), three with the intrusive Apache.
This reconciles session-30's optimism (which listed `samba 3.0.28a`/`apache2 2.2.8` as if the
corpus version-identified them passively — Samba has no matcher at all, and Apache is
intrusive-only): the *band* discriminates, as S30 found, but the corpus only hands the resolver
a version for five services. **It also corrects the service-ID figure carried since S26:** S26
recorded "6–7 of 11", counting services *identified* (including versionless telnet/Postfix/VNC);
the version-yielding number that matters for matching and release resolution is **5/11**, not
6–7 (and never 8 — S26 explicitly rejected that count). That is a **B22 service-identification
gap (backlog B28), not a resolver limitation** — the resolver correctly abstains on what it is
not given. The number that matters on a real host is the version-yield: **5 of 11**.

**Status (session-30): the BAND half is confirmed to work; the resolver is buildable on the
advisory keyspace with no new feed.** Session-29's two queries killed the *suffix* bridge and
found the 18-package keyspace too sparse to test the band. Session-30 widened the import to the
full hardy set (537 USNs → 190 packages / 589 rows) and tested the band directly: **hardy's
upstream version band is unique in the keyspace for every one of Metasploitable's service
packages** — `openssh 4.7p1`, `samba 3.0.28a`, `vsftpd 2.0.6`, `mysql 5.0.51a`, `apache2 2.2.8`,
`postfix 2.5.1` — so observed upstream `4.7p1` resolves hardy with **no suffix and no per-release
rename map**. Per the sign-off rule ("if the band discriminates, no new feed is needed and the
resolver is buildable"), option **(b) release-baseline feed is NOT required**. Metasploitable is
a valid acceptance host: 3 of its services (OpenSSH, MySQL, Apache) band-match hardy and agree; 2
(Samba 3.0.20, vsftpd 2.3.4) are swapped-in vulnerable builds that match no release band and
abstain rather than mis-vote. Numbers in **Session-30 measurement** below. The re-decision among
(a)/(b)/(c) remains the operator's — but the data now points at (a)-via-band, not (b).

**Session-29 history (superseded by session-30 for the band, retained for the suffix):** the
two queries below killed the suffix bridge and found the narrow keyspace uninformative. That
still stands for the *suffix*; the *band* was untested then and is now confirmed.

## Problem

Advisory matching (P3.2, ADR-014) keys on `distro_release` — `hardy`, not `ubuntu`.
OS attribution (B21, ADR-061) reaches **family-only**: banners name the distro family
and never the release, so `Attribution.DistroRelease` is `nil` on every host today.
A family-only host is therefore unmatchable — the second, unmet half of P3.3's entry
condition (ADR-060). Release resolution is what closes it.

The knowledge plane now holds USN's release keyspace (`advisory_fixed_packages.distro_release`,
populated in P3.2). The premise of this design was that it makes package-version → release
resolution tractable **without a new feed**. The coverage queries below tested that premise
against real data and it did not hold at the scale imported.

## Measured coverage (session-29 dev-DB queries — the sign-off condition)

Two single queries, run before sign-off. Both determine whether the approach is buildable, not
merely unimplemented.

**Query 1 — keyspace coverage of the observed services.** The imported hardy keyspace currently
holds **18 distinct package names / 22 fixed-package rows** (USN-1467-1 plus ~20 recent hardy
USNs — the narrow P3.2 import): `apache2, cupsys, curl, freetype, glibc, gnupg, gnutls13,
libxml2, libxslt, linux, mysql-dfsg-5.0, openssl, perl, php5, poppler, postgresql-8.3, sudo,
tiff`. Intersected against Metasploitable's version-carrying services:

| observed service | keyspace analogue (hardy) |
|---|---|
| MySQL 5.0.51a-3ubuntu5 | **mysql-dfsg-5.0** ✓ |
| Apache 2.2.8 | apache2 ✓ *(but Apache was probe-gated on the host — not version-identified)* |
| OpenSSH 4.7p1 | — none |
| vsftpd 2.3.4 | — none |
| ProFTPD 1.3.1 | — none |
| Samba 3.0.20 | — none |
| Postfix | — none |

**Exactly one** observed-and-version-identified service intersects the current keyspace (MySQL).
This is the "if it is one, the finding is that P3.3 needs a wider import before it needs an
algorithm" outcome, confirmed. `openssh`/`samba`/`vsftpd`/`proftpd` have hundreds of real hardy
USNs; they are simply not in the narrow import. **Import breadth is the first prerequisite, and
it is a data task, not an algorithm task.**

**Query 2 — does the revision suffix survive into `services.version`?** The bridge needs the
suffix (`-3ubuntu5`) to reach the scorer. It survives **per service, and only for one family**:

- **MySQL / MariaDB:** stored **whole** — `5.0.51a-3ubuntu5`. The wire protocol packs the full
  Debian version string to a null byte and the capture group `(?P<version>[0-9][^\x00]*)` takes
  all of it (`internal/scanpoint/banners.go:227`); the only post-processing is `TrimSpace`
  (`internal/engines/fingerprint/match.go:132`). Suffix intact.
- **SSH:** the version group stops at the `-` and stores `4.7p1`; the `Debian-8ubuntu1` fragment
  is diverted into a separate `info` field and consumed as an OS-family hint (banners.go:88–100).
  **No suffix in `services.version`.**
- **vsftpd / ProFTPD / Postfix:** upstream-only or no version, and the banners carry no suffix.

Across the whole `services` table, **zero** rows carry a ubuntu/debian/`~` suffix today.

**The deeper finding the two queries expose together:** the bare suffix is not the
release-discriminating signal anyway. `-3ubuntu5` is not unique to hardy — revisions of that
shape appear across releases. What actually pins MySQL to the 8.04 era is the **package name**
`mysql-dfsg-5.0` (renamed to `mysql-5.1`, `mysql-server-5.5`, … in later releases). So the
signal is the package-name era, which requires exactly the **upstream-product → Ubuntu-package
map** (option (a)) that the approved bridge set out to avoid — or a **release-baseline feed**
(the originally-rejected option B). For the majority of packages, whose name is stable across
releases (`openssh`, `samba`, `apache2`), the advisory keyspace cannot discriminate release at
all, because neither their name nor an available suffix distinguishes one release from another.

**Conclusion:** as written — advisory keyspace + suffix/band bridge, no product→package map — the
design resolves Metasploitable on the single MySQL coincidence and does not generalize. A
one-package resolution dressed as a scorer is the plausible-spec-vs-real-spec line this project
exists to hold. Sign-off is withheld pending the re-decision below.

## Session-30 measurement — widen the import, then test the band

The session-29 conclusion above was drawn against an 18-package keyspace that contained none of
`openssh`/`samba`/`vsftpd`/`proftpd`, so the *band* half was never tested — only the suffix.
Session-30 widened the import and tested it. Build: nothing.

**Task 1 — widened hardy import.** Full hardy set fetched by paginating the existing CLI at 20
notices/page (`--offset 0..520`), 27 pages, **537 advisories**. No bound was hit or needed
raising: 20 notices/page is far under `MAX_NOTICES=5000` and the 64 MB body cap, so the doctrine
held without a deliberate raise. Resulting keyspace:

- **hardy: 190 distinct packages / 589 fixed-package rows** (was 18 / 22).
- The wide hardy import also co-populated 12 releases that hardy USNs co-list (dapper→quantal),
  which is what made the band test possible without extra fetches.

**Task 2 — does the upstream band discriminate release? YES.** Each package's fixed versions per
release, upstream band (the part before `-Nubuntu`):

| package | hardy band | other releases in keyspace | hardy band unique? |
|---|---|---|---|
| openssh | **4.7p1** | feisty 4.3p2, gutsy 4.6p1 | ✓ |
| samba | **3.0.28a** | dapper 3.0.22, feisty 3.0.24, gutsy 3.0.26a, intrepid 3.2.3, jaunty 3.3.2, karmic 3.4.0, lucid 3.4.7, maverick 3.5.4, natty 3.5.8, oneiric 3.5.11 | ✓ |
| vsftpd | **2.0.6** | dapper 2.0.4, karmic 2.2.0, lucid 2.2.2, maverick 2.3.0 | ✓ |
| mysql-dfsg-5.0 | **5.0.51a** | dapper 5.0.22, gutsy 5.0.45, intrepid 5.0.67, jaunty 5.1.30really5.0.75 | ✓ |
| apache2 | **2.2.8** | dapper 2.0.55, gutsy 2.2.4, intrepid 2.2.9, … precise **2.2.22**, quantal **2.2.22** | ✓ for hardy |
| postfix | **2.5.1** | dapper 2.2.10 … natty 2.8.2 | ✓ (no observed version though) |

No other release in the keyspace shares hardy's band for any of these — because Ubuntu bumps the
upstream version every release, the band alone pins the release, **with no suffix and no rename
map**. This is the half session-29 never reached, and it answers the whole question: the band
discriminates. The honest general limitation the same data shows: two frozen adjacent releases
can share a band (`apache2 2.2.22` in **both** precise and quantal), so the band is not a
universal 1:1 — but it does not collide on any hardy package, so hardy resolution is unaffected.
Coverage is a function of how many releases are imported (broad per-release import, as Task 1
did for hardy); a release absent from the keyspace yields honest abstention, never a wrong
release.

**Task 3 — is Metasploitable a valid acceptance host? Yes, with recorded dissent.** Observed
service version vs hardy's band:

| service | observed | hardy band | consistent with hardy? |
|---|---|---|---|
| OpenSSH | 4.7p1 | 4.7p1 | ✓ |
| MySQL | 5.0.51a | 5.0.51a | ✓ |
| Apache | 2.2.8 | 2.2.8 | ✓ |
| Samba | **3.0.20** | 3.0.28a | ✗ older than any release's band |
| vsftpd | **2.3.4** | 2.0.6 | ✗ the backdoored build, above hardy's band |
| ProFTPD | 1.3.1 | *(no proftpd USN in the set at all)* | — no analogue |
| Postfix | *(banner carries no version)* | 2.5.1 | — no vote |

Three services (OpenSSH, MySQL, Apache) band-match hardy and **agree**; the two mismatches are
Metasploitable-2's hand-swapped vulnerable builds (Samba 3.0.20 predates every release's band;
vsftpd 2.3.4 is the 2011 backdoored tarball, above hardy's 2.0.6). Under exact-band matching both
**abstain** — they match no release, so they do not mis-vote; they surface as recorded dissent,
which is exactly what B21's provenance model is for. So the host resolves cleanly to `ubuntu804`
on a 3-vote agreement and does **not** need replacing — it is arguably a better test than a
pristine host because it exercises agreement and dissent at once.

## Decisions taken in the design pass

1. **Source of truth: the advisory keyspace already in the DB** (`advisory_fixed_packages`).
   Not a new release-baseline feed (authoritative but a second pipeline to build and store),
   and not version-string heuristics alone (the fragile banner-inference class B21 already
   showed breaks — `Debian-8ubuntu1` read as Debian). The keyspace is free and available now.
   Its honest limit: it is **sparse** (only packages that had advisories) and stores **fixed**
   versions, not shipped baselines — so it rules a release *in* better than *out*, and the
   resolver must stay unresolved rather than guess when the signal is thin.

2. **Bridge: version-suffix + upstream-version band as the primary release signal**, classified
   against what the keyspace shows per release. **No upstream-product → Ubuntu-package map** —
   package renames across releases (`mysql-dfsg-5.0` → `mysql-5.1` → `mysql-server-5.5`) are the
   whole problem, and a map that must track them is a maintenance artifact that will be wrong.
   A package-name match is used only where the observed data already carries the Ubuntu package
   name. This keeps the resolver on "what the knowledge plane knows" (decision 1).

   **↳ Overturned by Query 2 (see Measured coverage).** The suffix survives only for MySQL, and
   the bare suffix is not release-discriminating regardless — the discriminating signal is the
   package-name era, which needs the very product→package map this decision rejected. Decision 2
   does not survive contact with the data.

## Shape — mirrors B21's pure-decision + correlate-gathering split (CONTINGENT — see Re-decision)

B21's pattern is the template and should be followed so there is one place to read and one ADR
to revise:

1. **Store read (new, `internal/store/advisories.go`):** `ReleasesForPackage(...)` over
   `advisory_fixed_packages` — given an observed package (upstream band and/or Ubuntu version
   suffix), return the `distro_release`(s) the keyspace shows as consistent, each with a match
   strength (a package that exists under only one release-era is a strong vote; a bare
   `-NubuntuM` suffix that many releases share is weak/none). Global-table read from **inside a
   tenant `Read`**, exactly like `FixesFor` — the ADR-030-anticipated case, no unscoped primitive.

2. **Pure decision (new, `internal/domain/attribution.go`, sibling of `AttributeOS`):**
   `ResolveRelease(family, votes)` → fills `Attribution.DistroRelease` (already the nullable
   third state on the type). Each observed package casts a release vote; the verdict is the
   release the votes agree on, confidence = agreement strength, provenance reusing the
   `contributed` / `agreed` / `ignored` roles. Empty or conflicting votes → `DistroRelease` stays
   `nil` (family-only). **No fabrication** — B21's principle; the honest outcome of thin data is
   still family-only, which is unmatched but not wrong.

3. **Correlate wiring (`internal/correlate`):** after `AttributeOS` sets the family, gather the
   release votes from the observed service-ID versions (B22's product+version output), read the
   keyspace per package, call `ResolveRelease`, and promote the release onto the asset. **Runs
   only under a known family** — release is far less ambiguous once the family is fixed, and it
   avoids resolving a release for a host whose family is unknown.

## Acceptance

Metasploitable resolves to **`ubuntu804`** from its measured packages (`mysql-dfsg-5.0
5.0.51a-3ubuntu5` and the other B22/B24 signals), measured live and promoted to the asset — and
**then the whole chain lights up end to end**: family + release resolved → the P3.2 advisory
match (`FixesFor` + the dpkg comparator) → a real CVE-backed finding on a real host. That is the
P3.3 payoff, and it is the first time family, release, comparator, and advisory data all meet on
one real host.

Measure which signal actually resolves Metasploitable and report it — do not tune the resolver
to the sample (the corpus-gate discipline, §5.5/§5.6). The expectation: hardy's bare `-3ubuntu5`
suffix is weakly discriminating (many releases carry `-NubuntuM`), so the resolving vote is
likely the **upstream-version band + package-era** (`mysql-dfsg-5.0` existing only in the
8.04-era keyspace), not the bare suffix. If it resolves on a different signal than expected,
that is a finding about the keyspace's discriminating power, recorded, not smoothed over.

## Re-decision (updated by session-30's band test) — the operator's call

Session-29 leaned toward (b) a new feed. **Session-30's band test removes that need.** The band
discriminates hardy on every service package, so the resolver is buildable on the advisory
keyspace with no baseline feed. The choices, re-weighted against the numbers:

- **(a) advisory keyspace + upstream-BAND matching — now the recommended path.** Not the
  suffix (dead) and not a per-release rename map (the session-29 objection). The signal is the
  **upstream version band**, which Ubuntu bumps every release, so `4.7p1` ⇒ hardy directly. What
  it needs, both modest:
  1. **Broad per-release import** (Task 1's pagination, run per release the fleet might meet) so
     the band has releases to be unique *against*. Absent releases → honest abstention, not a
     wrong answer. This also lifts P2/P3.2 advisory-matching coverage regardless of P3.3.
  2. **A light product→package association** (`OpenSSH`→`openssh`, `MySQL`→`mysql*`,
     `Apache`→`apache2`) to scope the band search to the right package family. This is small and
     mostly stable — *not* the per-release rename table that was feared; band matching tolerates
     the `mysql-dfsg-5.0`→`mysql-5.1` rename because it matches on the upstream band, not the
     exact name.
- **(b) Release-baseline feed — no longer necessary.** It remains the most *authoritative*
  option (exact shipped versions, resolves stable-named packages that never had a USN), and the
  honest gap in (a) is real: a package with no advisory under a release casts no band vote there.
  But the band test shows (a) resolves the acceptance host and the common services without it, so
  (b) is an enhancement, not a prerequisite. Weigh it only if (a)'s advisory-only coverage proves
  too thin in practice.
- **(c) single-signal-honest — superseded.** Session-29 feared resolution rode one package
  (MySQL). Task 3 shows three independent services agree on hardy, so (c)'s pessimism no longer
  holds; (a) is the honest version of what (c) was reaching for.

**The Phase-4 alternative you named still stands as the ceiling:** credentialed assessment reads
`/etc/os-release` and answers this exactly rather than inferring it. (a) is unauthenticated
inference with recorded confidence/dissent (B21's model); it is right for the MVP's
unauthenticated posture, and Phase-4 credentialed release is strictly better when it lands. The
band test means you are **no longer forced to choose between a second inference pipeline (b) and
pulling Phase-4 forward** — (a) is buildable now on what exists.

**Whether `ResolveRelease` needs an ADR:** yes — the band-matching precedence and the
resolved-vs-candidate threshold are decisions with review triggers (the apache2 precise/quantal
band collision is precisely the kind of case that ADR would name). That ADR is written when (a)
is built, not now.
