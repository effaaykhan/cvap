# P3.3 release resolution — design (B25)

**Status: NOT signed off — two coverage queries against the dev DB (session-29) found the
design is not buildable as written.** The direction (resolve release from the advisory
keyspace, bridge by version-suffix + band) was approved *before* the queries were run; the
queries were the condition of sign-off and they came back negative. See **Measured coverage**
below. The corrected reading: P3.3 needs a **wider import** before it needs a scorer, and the
**suffix bridge does not generalize** — the release-discriminating signal is the package name,
not the suffix, and that reintroduces the product→package map the design set out to avoid. This
doc now records the numbers and the re-decision they force, rather than a plan to build.

## Problem

Advisory matching (P3.2, ADR-014) keys on `distro_release` — `hardy`, not `ubuntu`.
OS attribution (B21, ADR-061) reaches **family-only**: banners name the distro family
and never the release, so `Attribution.DistroRelease` is `nil` on every host today.
A family-only host is therefore unmatchable — the second, unmet half of P3.3's entry
condition (ADR-060). Release resolution is what closes it.

The knowledge plane now holds USN's release keyspace (`advisory_fixed_packages.distro_release`,
populated in P3.2). The premise of this design was that it makes package-version → release
resolution tractable **without a new feed**. The coverage queries below tested that premise
against real data and it did not hold at the scale imported.

## Measured coverage (session-29 dev-DB queries — the sign-off condition)

Two single queries, run before sign-off. Both determine whether the approach is buildable, not
merely unimplemented.

**Query 1 — keyspace coverage of the observed services.** The imported hardy keyspace currently
holds **18 distinct package names / 22 fixed-package rows** (USN-1467-1 plus ~20 recent hardy
USNs — the narrow P3.2 import): `apache2, cupsys, curl, freetype, glibc, gnupg, gnutls13,
libxml2, libxslt, linux, mysql-dfsg-5.0, openssl, perl, php5, poppler, postgresql-8.3, sudo,
tiff`. Intersected against Metasploitable's version-carrying services:

| observed service | keyspace analogue (hardy) |
|---|---|
| MySQL 5.0.51a-3ubuntu5 | **mysql-dfsg-5.0** ✓ |
| Apache 2.2.8 | apache2 ✓ *(but Apache was probe-gated on the host — not version-identified)* |
| OpenSSH 4.7p1 | — none |
| vsftpd 2.3.4 | — none |
| ProFTPD 1.3.1 | — none |
| Samba 3.0.20 | — none |
| Postfix | — none |

**Exactly one** observed-and-version-identified service intersects the current keyspace (MySQL).
This is the "if it is one, the finding is that P3.3 needs a wider import before it needs an
algorithm" outcome, confirmed. `openssh`/`samba`/`vsftpd`/`proftpd` have hundreds of real hardy
USNs; they are simply not in the narrow import. **Import breadth is the first prerequisite, and
it is a data task, not an algorithm task.**

**Query 2 — does the revision suffix survive into `services.version`?** The bridge needs the
suffix (`-3ubuntu5`) to reach the scorer. It survives **per service, and only for one family**:

- **MySQL / MariaDB:** stored **whole** — `5.0.51a-3ubuntu5`. The wire protocol packs the full
  Debian version string to a null byte and the capture group `(?P<version>[0-9][^\x00]*)` takes
  all of it (`internal/scanpoint/banners.go:227`); the only post-processing is `TrimSpace`
  (`internal/engines/fingerprint/match.go:132`). Suffix intact.
- **SSH:** the version group stops at the `-` and stores `4.7p1`; the `Debian-8ubuntu1` fragment
  is diverted into a separate `info` field and consumed as an OS-family hint (banners.go:88–100).
  **No suffix in `services.version`.**
- **vsftpd / ProFTPD / Postfix:** upstream-only or no version, and the banners carry no suffix.

Across the whole `services` table, **zero** rows carry a ubuntu/debian/`~` suffix today.

**The deeper finding the two queries expose together:** the bare suffix is not the
release-discriminating signal anyway. `-3ubuntu5` is not unique to hardy — revisions of that
shape appear across releases. What actually pins MySQL to the 8.04 era is the **package name**
`mysql-dfsg-5.0` (renamed to `mysql-5.1`, `mysql-server-5.5`, … in later releases). So the
signal is the package-name era, which requires exactly the **upstream-product → Ubuntu-package
map** (option (a)) that the approved bridge set out to avoid — or a **release-baseline feed**
(the originally-rejected option B). For the majority of packages, whose name is stable across
releases (`openssh`, `samba`, `apache2`), the advisory keyspace cannot discriminate release at
all, because neither their name nor an available suffix distinguishes one release from another.

**Conclusion:** as written — advisory keyspace + suffix/band bridge, no product→package map — the
design resolves Metasploitable on the single MySQL coincidence and does not generalize. A
one-package resolution dressed as a scorer is the plausible-spec-vs-real-spec line this project
exists to hold. Sign-off is withheld pending the re-decision below.

## Decisions taken in the design pass

1. **Source of truth: the advisory keyspace already in the DB** (`advisory_fixed_packages`).
   Not a new release-baseline feed (authoritative but a second pipeline to build and store),
   and not version-string heuristics alone (the fragile banner-inference class B21 already
   showed breaks — `Debian-8ubuntu1` read as Debian). The keyspace is free and available now.
   Its honest limit: it is **sparse** (only packages that had advisories) and stores **fixed**
   versions, not shipped baselines — so it rules a release *in* better than *out*, and the
   resolver must stay unresolved rather than guess when the signal is thin.

2. **Bridge: version-suffix + upstream-version band as the primary release signal**, classified
   against what the keyspace shows per release. **No upstream-product → Ubuntu-package map** —
   package renames across releases (`mysql-dfsg-5.0` → `mysql-5.1` → `mysql-server-5.5`) are the
   whole problem, and a map that must track them is a maintenance artifact that will be wrong.
   A package-name match is used only where the observed data already carries the Ubuntu package
   name. This keeps the resolver on "what the knowledge plane knows" (decision 1).

   **↳ Overturned by Query 2 (see Measured coverage).** The suffix survives only for MySQL, and
   the bare suffix is not release-discriminating regardless — the discriminating signal is the
   package-name era, which needs the very product→package map this decision rejected. Decision 2
   does not survive contact with the data.

## Shape — mirrors B21's pure-decision + correlate-gathering split (CONTINGENT — see Re-decision)

B21's pattern is the template and should be followed so there is one place to read and one ADR
to revise:

1. **Store read (new, `internal/store/advisories.go`):** `ReleasesForPackage(...)` over
   `advisory_fixed_packages` — given an observed package (upstream band and/or Ubuntu version
   suffix), return the `distro_release`(s) the keyspace shows as consistent, each with a match
   strength (a package that exists under only one release-era is a strong vote; a bare
   `-NubuntuM` suffix that many releases share is weak/none). Global-table read from **inside a
   tenant `Read`**, exactly like `FixesFor` — the ADR-030-anticipated case, no unscoped primitive.

2. **Pure decision (new, `internal/domain/attribution.go`, sibling of `AttributeOS`):**
   `ResolveRelease(family, votes)` → fills `Attribution.DistroRelease` (already the nullable
   third state on the type). Each observed package casts a release vote; the verdict is the
   release the votes agree on, confidence = agreement strength, provenance reusing the
   `contributed` / `agreed` / `ignored` roles. Empty or conflicting votes → `DistroRelease` stays
   `nil` (family-only). **No fabrication** — B21's principle; the honest outcome of thin data is
   still family-only, which is unmatched but not wrong.

3. **Correlate wiring (`internal/correlate`):** after `AttributeOS` sets the family, gather the
   release votes from the observed service-ID versions (B22's product+version output), read the
   keyspace per package, call `ResolveRelease`, and promote the release onto the asset. **Runs
   only under a known family** — release is far less ambiguous once the family is fixed, and it
   avoids resolving a release for a host whose family is unknown.

## Acceptance

Metasploitable resolves to **`ubuntu804`** from its measured packages (`mysql-dfsg-5.0
5.0.51a-3ubuntu5` and the other B22/B24 signals), measured live and promoted to the asset — and
**then the whole chain lights up end to end**: family + release resolved → the P3.2 advisory
match (`FixesFor` + the dpkg comparator) → a real CVE-backed finding on a real host. That is the
P3.3 payoff, and it is the first time family, release, comparator, and advisory data all meet on
one real host.

Measure which signal actually resolves Metasploitable and report it — do not tune the resolver
to the sample (the corpus-gate discipline, §5.5/§5.6). The expectation: hardy's bare `-3ubuntu5`
suffix is weakly discriminating (many releases carry `-NubuntuM`), so the resolving vote is
likely the **upstream-version band + package-era** (`mysql-dfsg-5.0` existing only in the
8.04-era keyspace), not the bare suffix. If it resolves on a different signal than expected,
that is a finding about the keyspace's discriminating power, recorded, not smoothed over.

## Plug-in points (verified against the code, session-29)

- `internal/domain/attribution.go` — `Attribution.DistroRelease *string` already exists (the
  three-state model); `AttributeOS` is pure. Add `ResolveRelease` beside it, same purity.
- `internal/store/advisories.go` — `FixesFor` is the read pattern to copy for `ReleasesForPackage`.
- `internal/correlate` — the path that already calls `AttributeOS` and promotes the family is
  where release gathering + promotion is added.

The **Shape** and **Acceptance** sections above describe the resolver as it would be built *if*
the approach were viable. They are retained for reference but are **contingent on the re-decision
that the coverage queries now force** — do not build against them until that is settled.

## Re-decision the coverage queries force (before any build)

The queries collapsed the "advisory keyspace + suffix/band, no map" plan. The real choices now:

1. **Wider import is a prerequisite either way.** Import the full hardy USN set (hundreds of
   notices), not the ~20 recent ones, so `openssh`/`samba`/`vsftpd`/`proftpd`/`postfix` have
   keyspace analogues at all. Until then the intersection is one package and there is nothing to
   score. This is a P3.2 import-scope task, cheap, and it should happen first — it also raises
   real advisory-matching coverage regardless of P3.3. **Note the honest limit:** a wider import
   raises *matching* coverage, but for release *resolution* it only helps packages whose name or
   surviving version actually discriminates a release — which the queries showed is few.

2. **Then pick the release signal, knowing the suffix bridge failed:**
   - **(a) Product→package map + package-era.** The signal that actually works for MySQL
     (`mysql-dfsg-5.0` ⇒ 8.04-era). Precise for renamed packages; useless for stable-named ones
     (`openssh`), and a map to maintain across releases. This is the rejected option the data
     rehabilitates — but it resolves *few* packages.
   - **(b) Release-baseline feed** (originally-rejected option B). The authoritative answer:
     each release's shipped package versions, so *any* observed (package, version) resolves a
     release by exact baseline membership — no dependence on a surviving suffix or a rename. It
     is a second knowledge pipeline, but it is the only option that generalizes to the
     stable-named majority. **The queries make the case for B that the design pass argued
     against.**
   - **(c) Accept release resolution is single-signal today and scope P3.3 to that honestly.**
     Resolve release only where a strong per-package signal exists (MySQL's era + suffix), mark
     everything else family-only, and state that "resolved" means "one package pinned it." Cheap
     and honest, but it is barely a resolver and it leaves Metasploitable resolved by coincidence.

3. **Whether `ResolveRelease` needs an ADR** — moot until (a)/(b)/(c) is chosen; the choice is
   itself the ADR-worthy decision now, superseding this design's premise.

My read after the measurement: **(1) wider import first (do it regardless), then (b) a
release-baseline feed** is the only path that resolves the stable-named majority rather than
riding the MySQL coincidence — which means P3.3 likely does need the new feed the design pass
hoped to avoid. That is a real reversal and it belongs to the operator's call, not mine.
